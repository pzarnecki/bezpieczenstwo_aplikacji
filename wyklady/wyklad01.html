Spojrzenie pod maskę

To nie był ekspres do kawy. To był podatny serwer Linux.

Dlaczego napastnik nie przejmuje się tym, do czego urządzenie służy w kuchni

1. Wbudowany stos sieciowy
Urządzenie posiadało miniaturowy procesor z jądrem Linuksa, pełny stos TCP/IP, działający serwer HTTP oraz lokalny demon serwisowy otwarty na portach 80 i 8080.
2. Grzechy kodu i architektury
Brak autoryzacji na wewnętrznym REST API, twardo zakodowane poświadczenia serwisowe (hardcoded credentials) oraz brak bezpiecznego mechanizmu podpisywanych aktualizacji OTA.
3. Monetyzacja ataku
Ekspres generował ruch w wolumetrycznych atakach DDoS, pośredniczył w nielegalnym tunelowaniu proxy oraz brał udział w masowym skanowaniu kolejnych podsieci.
Wniosek techniczny: Dla atakującego nie ma znaczenia etykieta marketingowa („Smart Coffee Maker”, „Baza SQL banku”, „Mikroserwis zamówień”). Każdy proces posiadający interfejs sieciowy i podatny kod to po prostu darmowy procesor, pamięć RAM i łącze 100 Mb/s.
Architektura systemów

Iluzja twierdzy: Dlaczego firewall nie uratuje aplikacji?

Tradycyjne bezpieczeństwo obwodowe (Perimeter Security) w zderzeniu z nowoczesną siecią

Model historyczny: Zamek i Fosa

• Założenie: Sieć wewnętrzna (LAN) jest bezpieczna, zewnętrzna (WAN) jest wroga.

• Na brzegu sieci stoi Firewall (zapora sieciowa L3/L4).

• Wystarczy zablokować nieużywane porty, a serwery wewnątrz mogą sobie bezgranicznie ufać.

Model całkowicie martwy we współczesnych architekturach.

Współczesna rzeczywistość aplikacji

• Porty 80 (HTTP) i 443 (HTTPS) muszą być z definicji otwarte na cały świat.

• Aplikacje to rozproszona siatka mikroserwisów, chmur publicznych, API i workerów.

• Ruch szyfrowany TLS: firewall brzegowy widzi jedynie strumień bajtów, nie rozumiejąc złośliwego ładunku w JSON.

Złota reguła bezpieczeństwa systemów:
Zapora sieciowa chroni porty. Bezpieczeństwo aplikacji chroni logikę i dane. Atakujący wchodzi legalnie przez port 443 i rozmawia z Twoim API w sposób zgodny ze specyfikacją protokołu!
Wektory ataków i krajobraz 2026/2027

Dlaczego celem numer 1 jest warstwa aplikacji (L7)?

Nikt nie łamie AES-256 brute-forcem. Atakuje się błędy w logice, łańcuch dostaw i kod generowany przez AI.

1. Skład kodu
W typowej aplikacji zaledwie 10–20% kodu to kod autorski. Pozostałe 80–90% to zewnętrzne pakiety (npm, PyPI, Maven, Docker).
2. Logika biznesowa
WAF potrafi zablokować proste SQLi, ale nie wie, że użytkownik ID=15 nie powinien pobierać faktury użytkownika ID=16 (IDOR / BOLA).
3. Kod z asystentów AI
AI Package Hallucination / Slopsquatting — atakujący rejestrują w npm wymyślone przez LLM pakiety. Bezkrytyczne wklejanie podatnego kodu AI.
4. Presja Time to Market
Funkcjonalności biznesowe mają priorytet. Testy bezpieczeństwa tradycyjnie spychane na koniec sprintu — albo pomijane aż do incydentu.

Słowniczek pojęć: Najważniejsze skróty bezpieczeństwa aplikacji
Skrót Pełna nazwa angielska Znaczenie techniczne w architekturze i audycie
L7 Layer 7 (Application Layer) Siódma warstwa modelu OSI (HTTP, WebSocket, gRPC). Tu przetwarzana jest logika biznesowa, autoryzacja i parsowanie danych użytkownika.
WAF Web Application Firewall Zapora aplikacyjna badająca ruch HTTP w poszukiwaniu znanych sygnatur ataków. Blokuje popularne exploity, ale nie weryfikuje praw dostępu w relacjach obiektowych.
IDOR Insecure Direct Object Reference Błąd autoryzacji horyzontalnej: aplikacja przyjmuje identyfikator z zewnątrz (np. ?id=123) i zwraca dane bez sprawdzenia, czy zalogowany użytkownik jest ich właścicielem.
BOLA Broken Object Level Auth. Nowoczesne określenie błędu IDOR w świecie interfejsów REST API (kategoria nr 1 w oficjalnym rankingu OWASP API Security Top 10).
ORM Object-Relational Mapping Warstwa abstrakcji nad bazą danych (np. SQLAlchemy, Hibernate, Prisma). Chroni przed klasycznym SQLi poprzez automatyczne zapytania parametryzowane.
CVE Common Vulnerabilities & Exposures Globalny słownik powszechnie znanych luk bezpieczeństwa. Każda zidentyfikowana luka otrzymuje unikalny identyfikator (np. CVE-2024-3094).
SBOM Software Bill of Materials Maszynowo czytelna lista (np. w formacie CycloneDX lub SPDX) wszystkich bibliotek, zależności tranzytywnych i modułów składających się na aplikację.
ReDoS Regular Expression Denial of Service Odmowa usługi spowodowana podatnym wyrażeniem regularnym, którego ewaluacja dla spreparowanego tekstu wymaga wykładniczej liczby operacji (backtracking).

Szczegółowa anatomia techniczna podatności OWASP Top 10
A01 Broken Access Control & SSRF
Mechanizm ataku: Zalogowany klient 104 wysyła żądanie GET /api/faktury/105. Aplikacja pobiera fakturę bez walidacji relacji do sesji (IDOR/BOLA). Atak SSRF wymusza na serwerze odpytanie instancji metadanych chmury http://169.254.169.254/latest/meta-data/ i wyciek tokenów IAM.
Obrona: Wymuszenie autoryzacji na poziomie bazy: WHERE id = :id AND user_id = :user_id (scenariusz ten rozwiązujemy praktycznie w Zadaniu 8 projektu KrasnalShop) oraz blokowanie ruchu wychodzącego do sieci prywatnych.
A02 Security Misconfiguration
Mechanizm ataku: Domyślne hasła administratora, publiczne buckety S3, brak nagłówków bezpieczeństwa (HSTS, CSP), włączony tryb DEBUG na środowisku produkcyjnym ujawniający hasła w zmiennych środowiskowych.
Obrona: Automatyczny hardening kontenerów, skanery IaC (Checkov, Trivy) oraz domyślne wyłączanie nieużywanych portów.
A03 Software Supply Chain Failures
Mechanizm ataku: Wstrzyknięcie złośliwego kodu do publicznego pakietu open-source (Typosquatting, przejęcie konta dewelopera npm, Dependency Confusion). Kod złośliwy wykonuje się podczas instalacji lub w runtime aplikacji.
Obrona: Pliki lock z sumami kontrolnymi (package-lock.json), automatyczne skanery SCA (pip-audit, Trivy, npm audit), podpisywanie kontenerów (Cosign).
A04 Cryptographic Failures
Problem: Szybkie hashowanie haseł w MD5 lub SHA-256 bez soli (łamane tablicami tęczowymi w sekundy), brak TLS 1.3.
Obrona: Wolne algorytmy pamięciożerne z unikalną solą: Argon2id (standard branżowy) lub bcrypt.
A05 Injection (Wstrzyknięcia)
Problem: Konkatenacja zapytań SQL ze stringami użytkownika lub brak kodowania HTML wyjścia (XSS).
Obrona: Prepared Statements w ORM oraz silna polityka Content-Security-Policy.
A06-A10 Insecure Design, Auth, Integrity, Logging, Exceptions
Błędy koncepcyjne (A06), słabe uwierzytelnianie podatne na brute-force (A07), niebezpieczna deserializacja obiektów np. pickle.loads() w Pythonie (A08), brak logów zdarzeń uniemożliwiający reakcję na włamanie (A09) oraz ujawnianie ścieżek serwera w StackTrace (A10).
Projektowanie systemów

Modelowanie zagrożeń: Metodyka STRIDE

Jak psuć aplikację na tablicy, zanim napiszemy pierwszą linijkę kodu

S Spoofing (Podszywanie się)
Czy napastnik może podać się za innego użytkownika lub mikroserwis? Obrona: silne uwierzytelnianie, mTLS, tokeny z podpisem.
T Tampering (Manipulacja)
Czy przesyłane parametry lub dane w bazie mogą zostać zmodyfikowane w locie? Obrona: podpisy HMAC, integralność, TLS.
R Repudiation (Wypieralność)
Czy użytkownik może wyprzeć się wykonania operacji finansowej? Obrona: audytowalne logi operacji, niezmienne zdarzenia.
I Information Disclosure
Czy wrażliwe dane wyciekają w odpowiedziach API lub logach? Obrona: szyfrowanie at-rest, minimalizacja danych, maskowanie.
D Denial of Service
Czy aplikację można zablokować wyczerpaniem procesora lub bazy? Obrona: Rate Limiting, timeouty, kolejki asynchroniczne.
E Elevation of Privilege
Czy zwykły użytkownik może nadać sobie uprawnienia administratora? Obrona: weryfikacja ról (RBAC/ABAC) po stronie serwera.
STRIDE w praktyce: Scenariusze ataków i metody obrony
S Spoofing — Podszywanie się pod tożsamość
Scenariusz: Wstrzyknięcie fałszywego nagłówka X-Forwarded-For: 127.0.0.1 lub przesłanie tokenu JWT ze zmienionym nagłówkiem "alg": "none".
Mitigacja: Weryfikacja podpisu asymetrycznym kluczem publicznym (RS256 / EdDSA) oraz wzajemne uwierzytelnianie mTLS pomiędzy usługami.
T Tampering — Manipulacja parametrami zamówienia
Scenariusz: Formularz zamówienia przekazuje ukryte pole <input type="hidden" name="cena" value="999.00">. Atakujący zmienia wartość na 0.01 w konsoli DevTools.
Mitigacja: Cena pobierana wyłącznie z zaufanej bazy serwera na podstawie ID produktu. Żadnych krytycznych danych biznesowych w ukrytych polach HTML!
R Repudiation — Wypieralność działań
Scenariusz: Użytkownik zleca przelew środków, po czym twierdzi, że tego nie zamawiał, a logi serwera nie zapisują identyfikatora sesji ani sumy kontrolnej transakcji.
Mitigacja: Niezmienne logi audytowe (WORM — Write Once, Read Many) przesyłane strumieniowo do zewnętrznego systemu SIEM.
D & E Denial of Service oraz Elevation of Privilege
DoŚ: Endpoint /api/produkty?limit=1000000 powoduje wyczerpanie pamięci RAM serwera Node.js i zawieszenie aplikacji.
Elevation: Przesłanie w JSON pola {"role": "admin"} podczas rejestracji klienta (podatność Mass Assignment).
Mitigacja: Sztywne limity paginacji (max 50 rekordów) oraz restrykcyjne DTO/szablony wejścia odrzucające nieautoryzowane pola.
Automatyzacja w DevSecOps

Triada automatyzacji testów bezpieczeństwa

Ręczny audyt raz w roku to za mało. Jak automatyzować weryfikację w potoku CI/CD?

SAST
Static Application Security Testing

• Badanie kodu źródłowego bez jego uruchamiania (White-Box).

• Analizuje drzewo składniowe AST, wykrywa brak sanityzacji, niebezpieczne funkcje systemowe.

Narzędzia: Semgrep, SonarQube, Bandit

DAST
Dynamic Application Security Testing

• Badanie działającej aplikacji z zewnątrz (Black-Box).

• Wysyła sfuzzowane żądania HTTP, sprawdza reakcję na wstrzyknięcia i konfigurację nagłówków.

Narzędzia: OWASP ZAP, Burp Suite, Nuclei

SCA
Software Composition Analysis

• Analiza drzewa zależności i kontenerów (SBOM).

• Porównuje wersje bibliotek z publicznymi bazami znanych podatności (CVE/NVD).

Narzędzia: Trivy, pip-audit, npm audit, Snyk

Złota zasada: Żadne z tych narzędzi nie działa w próżni. Prawdziwe bezpieczeństwo w CI/CD to synergia: SAST (mój kod) + SCA (cudzy kod) + DAST (uruchomiony stos).
Zestawienie porównawcze: Podejścia testowe w praktyce
Kryterium techniczne SAST (Kod źródłowy) DAST (Uruchomiony serwer) SCA (Zależności open-source)
Perspektywa testu White-Box (pełen dostęp do repozytorium) Black-Box (brak wglądu w kod, tylko HTTP) Manifest / SBOM (graf zależności)
Czy wymaga uruchomienia? Nie (skanuje pliki tekstowe) Tak (musi działać środowisko i baza danych) Nie (analizuje pliki lock i obrazy Docker)
Pozycja w pipeline CI/CD Pre-commit hook, etap Pull Request Środowisko Staging / Test przed wydaniem Etap Build / tworzenie obrazu kontenera
Czas wykonania skanu Szybki (kilka do kilkudziesięciu sekund) Wolny (od kilkunastu minut do kilku godzin) Ekspresowy (od ułamka sekundy do kilku s)
Fałszywe alarmy (False Positives) Średni / Wysoki (wymaga strojenia reguł) Bardzo niski (weryfikuje realną odpowiedź HTTP) Niski (bazuje na skatalogowanych numerach CVE)

Dobre praktyki architektoniczne

Cztery filary Secure by Design

Zasady, które każdy projektant oprogramowania powinien traktować jak instynkt

1. Zasada najmniejszych uprawnień (Least Privilege)

Żaden proces, usługa ani użytkownik nie może posiadać większych praw niż absolutnie konieczne do wykonania zadania.

Dobre praktyki implementacji:

• Dyrektywa USER appuser w pliku Dockerfile (kontenery nigdy nie uruchamiają się jako root).

• Dedykowane konto bazy danych bez uprawnień DROP TABLE czy ALTER TABLE.

2. Obrona w głąb (Defense in Depth)

Bezpieczeństwo systemu nigdy nie może opierać się na pojedynczej linii obrony.

Dobre praktyki implementacji:

• Walidacja na frontendzie to wygoda dla usera (UX), nie bezpieczeństwo.

• Pełna walidacja w API + zapytania parametryzowane + uprawnienia na poziomie wiersza w bazie danych.

3. Nigdy nie ufaj danym wejściowym (Zero Trust Input)

Każdy bajt pochodzący z zewnątrz jest traktowany jako potencjalnie złośliwy ładunek.

Dobre praktyki implementacji:

• Brak zaufania do nagłówków Origin, Referer czy ciasteczek.

• Twarde schematy walidacji wejścia (Pydantic w Pythonie, Zod w TypeScript) odrzucające niespodziewane pola.

4. Bezpieczne ustawienia domyślne (Secure Defaults)

Aplikacja w stanie domyślnym musi być bezpieczna bez konieczności dodatkowej konfiguracji.

Dobre praktyki implementacji:

• Domyślna odmowa dostępu (Deny by Default) w regułach autoryzacji.

• Ciasteczka z flagami HttpOnly; Secure; SameSite=Strict włączonymi natywnie w frameworku.

Podsumowanie architektoniczne: Dobre oprogramowanie nie polega na łataniu dziur po testach penetracyjnych. Dobre oprogramowanie jest projektowane w sposób uniemożliwiający wystąpienie całej klasy podatności.
